# Changelog

All notable changes to zstack are documented here. Format follows [Keep a Changelog](https://keepachangelog.com/); versions use `MAJOR.MINOR.PATCH.MICRO`.

There is no `[Unreleased]` section: since 1.1.0.0 every PR opens its own version heading at merge time, written by `bun lib/version.ts claim` rather than by hand. Do not add one, and do not edit a version heading or VERSION/package.json directly — see [docs/user-guide/z-loop.md](docs/user-guide/z-loop.md#version-claiming).

## [1.3.0.2] - 2026-08-07

### Changed

Fix merge PR auto-close to avoid masquerading as a human action. Stop-lane now pre-empts the Done-gate transition, ensuring ticket state is confirmed before auto-close.

## [1.3.0.0] - 2026-08-07

### Added

Remove legacy pre-#322 transcript reader, cutting unused code paths and improving long-term maintainability.

## [1.2.2.0] - 2026-08-07

### Fixed

C3 of epic #321: the board is authoritative and state.json is a derived cache. Done requires the exact PR a merge verdict named observed MERGED on GitHub (pr-state --pr + loop confirm-merged; a positive not-merged answer parks the divergence, an unreadable one retries bounded). Dependencies satisfy on positive evidence only: a carried dep earns one targeted read, a gone dep satisfies only when its issue is CLOSED and parks the dependent when OPEN. A confirmed pid must also beat, so a harness outliving its drain cannot pin the loop lock. clean-retained previews and scopes. Same-login operator claims are held, not stolen. Ghost lanes stop with the divergence named, and the skip-qa crash window resyncs.

## [1.2.1.0] - 2026-08-07

### Fixed

C2 of epic #321: stage outcomes are verdict FILES, never prose. Each stage writes a schema-validated verdict.json into its run-scoped directory; the loop validates it against its own spawn record, routes missing/invalid to respawn-then-salvage, counts reviewer quorum off skeptic verdict files on disk, and composes skeptic briefs deterministically. Kills the forgeable QA-PASS (#312), the duplicate fence tracker (#314), unbounded stage returns (#262), the self-reported skeptic tally (#266), improvised skeptic briefs (#265), the prose post-conflict re-gate (#249), invisible late skeptic verdicts (#231), and prose-judged worker liveness (#257).

## [1.2.0.0] - 2026-08-07

### Added

C1 of epic #321: every artifact of a drain now lives under runs/<runId>/ and cost is keyed by run. A first ingest mints the id; z-cost takes --run-dir/--state-dir/--legacy instead of positional globs; the loop refuses v1 state files with a named remedy. Kills the glob-based cost family: attempt-collision overwrites (#210), cross-run Actual absorption (#212), the 365-dollar report on a 2-dollar batch (#309), z-cost's silent first-file pricing (#319), legacy-shape mis-bucketing (#211), the unverifiable #254 measurement (#261), and the inflated report total (#176).

## [1.1.1.0] - 2026-08-07

### Fixed

- **A stage that finishes its work no longer loses the ticket over where it put its exit marker (#307).** The loop read only the first line of a stage agent's final message, so a builder or QA agent that wrote a prose summary and put a correctly spelled `BUILT:` / `QA-PASS:` anywhere else was recorded as CONFUSED and its ticket Skipped — after the stage had spent its full budget, with the work committed and the suite green. That was the dominant failure of loop 16: 3 of 3 tickets, two models, two stage kinds, $2.33 paid for nothing merged. A marker on a line of its own is now read wherever it sits, which rescues 132 of the 507 real stage messages retained in this repo's transcripts with zero verdicts changed in any other direction.
- **A marker a stage was only QUOTING no longer reads as a verdict.** Markers inside a fenced code block, and payloads still carrying the contract's own `<placeholder>`, are ignored and reported as `only QUOTED its exit markers`. Fence tracking follows CommonMark, so a nested or info-string-carrying delimiter cannot re-open a block and expose the marker inside it.
- **`MERGED` is accepted only as the first or the closing line, and its note is only the PR URL.** It is the one verdict that is terminal and never re-read, so a merge agent narrating a failed gate can no longer mark a ticket Done over an unmerged branch, and model-authored prose can no longer land in the completion note's URL slot.
- **A reviewer's approval is scored off its own verdict line.** `confidence=` is the lowest value on the marker's own lines, so a number narrated in prose or quoted inside a pasted diff hunk cannot clear the safety gate, and a bare `REVIEW-APPROVE:` scores null and will not merge. `skeptics=` takes the lowest denominator found outside a fence, so an honest "only 1 of 3 came back" still blocks.
- **Two contradicting markers stop the ticket instead of shipping the first one.** A `REVIEW-APPROVE` followed by a `REVIEW-FINDINGS` is reported as unreadable and names both, rather than approving the diff its own next line calls defective.

### Changed

- **Stage prompts state the marker-position rule with a worked negative example**, and price the wait they ask for: the suite runs 128-234s against each stage's own watchdog budget, so a stage can see that running verification in the foreground fits.

## [1.1.0.0] - 2026-08-06

### Added

- Every PR claims its own version slot, so the manual release-only bump is gone. The merge stage's new Step 0 shells `bun lib/version.ts claim`, which reads `origin/<base>`'s VERSION and every open PR's claimed VERSION (one paginated GraphQL read through `lib/board.ts`, still the pack's only `gh` caller), derives the bump level from the ticket's own labels, writes VERSION + package.json + CHANGELOG.md, commits and pushes -- all before `gh pr create`, so gstack's `/review` has something to read when it does `git show HEAD:VERSION` and compares it against the next free slot. Until now that check was vacuous: with no bump on the branch every PR read as claiming the base version, indistinguishable from claiming nothing. The number is deterministic space and the agent is told so in as many words -- the ONE latent input is the CHANGELOG prose, which arrives via `--entry-file` because summarizing what shipped is genuinely a judgment call. The slot is the greatest of (base, every outstanding claim) bumped by level, NOT the base alone: bump the base and a `patch` ticket picks 1.0.2.0 while an open PR already holds 1.0.1.1, which is free today and a version that goes BACKWARDS the moment that PR lands last. Taking the max makes the pick strictly above every claim, so the collision loop other allocators need does not exist here; the cost is a gap in the sequence when a PR closes unmerged, which is cosmetic where a decreasing version is not. Levels come from labels (`breaking`->major, `enhancement`/`feature`->minor, `bug`/`fix`->patch, everything else->micro), highest label wins so GitHub's return order cannot change the answer, and `versionBumpLabels` in `~/.zstack/projects/<slug>/config.json` REPLACES that map for a project whose taxonomy reuses a default name differently. Step 0 runs ahead of the green gate on purpose -- it commits to the branch, and a gate run before it would stamp a verdict for a commit that is not the one merging (#248's whole premise) -- and the conflict path in step 2 re-runs the claim before re-running the gate, since resolving pulls the base VERSION in. Re-running on an unmoved queue is a no-op rather than a ratchet; a queue that moved above an existing claim re-points the CHANGELOG heading in place instead of inserting a second section. Every failure fails CLOSED and maps to BLOCKED: an unreadable queue (a null `repository`) throws rather than reading as an empty one, because "nobody claims anything" hands out the slot just above the base, which is precisely wrong when the real answer is "we could not see the queue". `[Unreleased]` retires with this entry -- the first claim rewrites that heading into the version actually shipping, which is what removes the stale release-only PR that resolved DESTRUCTIVELY against a moved base once already (#143). The one agent-authored input, the CHANGELOG prose itself, is validated before anything is written: an entry carrying its own `## [` heading is REFUSED, not stripped, because both the insert and the re-point paths key off that heading and one buried in prose moves the section boundary a later claim reads. A cross-model adversarial pass found five more before this shipped, each fixed with the regression pinned: a previous attempt that wrote the files and then failed to COMMIT was read as an existing claim on the retry (the branch version came off DISK), so the retry exited 0 having committed nothing and the PR was opened from a branch whose HEAD still carried the old version -- HEAD is the source of truth now and a dirty owned file is refused rather than written over; a commit that failed to PUSH was likewise reported as claimed forever, so the keep path is a verification that re-pushes rather than a no-op; `setPackageVersion` rewrote a NESTED `"version"` key appearing earlier in the file and left the package's own stale, silently, still valid JSON (reproduced, now verified by re-parsing); the worktree was only proven to be A git root, not THIS ticket's, so the base checkout and another lane's branch are both refused via the same `isLaneBranch` the merge gate binds with; and an `--entry-file` that was NAMED but missing fell back to the ticket title silently, losing the real entry. 80 gate tests in `tests/version.test.ts`, 7 more on the merge prompt, 6 on `openPrVersions`.
- A cumulative per-stage ceiling ends a lane no watchdog could (#256). `STAGE_CEILING_MINUTES` = 480: a lane whose CURRENT stage has held it that long parks Blocked, naming the stage, the elapsed minutes and the ceiling, whatever its worker keeps answering. This is what makes the watchdog's alive path terminate at all. An ALIVE probe refreshes `lastActivityMs` with no memory of the probes before it, so a worker that is wedged but still registered in the harness task list answers alive, the baseline resets, and the same lane is probed one budget later -- forever, holding its ticket, its worktree, its lane lock and one of the `maxLanes` slots. Every other retry in the pack is outcome-driven (`qaBounces`, `reviewBounces`, `quorumRetries`, `commitRetries`, `respawns`); elapsed time had none, so nothing ended that sequence but a human noticing. The bound needs a clock the heartbeat may not touch, so `LaneState` gains a fourteenth field, `stageStartedMs`, stamped by the three actions that place an agent on a lane (claim, advance, respawn) and by nothing else -- `recordActivity`, `recordProbe` and `recordOutcome` all leave it alone, pinned by a test, because moving it would rebuild the same unbounded loop inside the fix. Checked for every lane, NOT only inside the expiry branch: a worker probed alive a second ago is not silent, so a ceiling gated on silence would be unreachable on exactly the lanes it exists to end. Absent `stageStartedMs` (a pre-#256 state file) means no ceiling -- the fail-open direction, since a lane the loop cannot age must never be parked on a number it does not have. 480 is a MEASUREMENT: the longest stage agent that came to rest on a final answer on this machine ran 13,304,097 ms (3.7 hours, a real builder), over 939 stage-described spawns (p50 8.0m, p95 27.8m, p99 48.6m), and the same 2x-then-round-up rule gives 8 hours -- which is `SUBTREE_STALE_MS` exactly, the age at which lib/transcripts.ts already stops believing a transcript proves anything is running. The park carries `salvage: true` unconditionally (unlike the dead-worker paths, which set it only on a proven-dirty worktree): there is no probe here and so no worktree facts, the agent may still be writing files it never committed, and releasing the lane lock makes that worktree an orphan the next reconcile force-removes -- an empty patch costs one file, a discarded 8-hour worktree costs the ticket. A merge lane's note carries the H9 warning to check `gh pr view` before returning the ticket, since the PR may have landed before the agent wedged. A lane with a recorded outcome is never ceiling-parked (its stage finished; the machine is about to advance it).

### Changed

- `watchdogMinutes` is resolved PER STAGE (#256). One global number had to serve a merge stage that runs `gh pr merge` and a reviewer that sits blocked on three background skeptics, and measured, those two are 12x apart in how long they legitimately go quiet. The knob now takes either shape: a number (one budget for every stage -- what every config written before this carries, still byte-identical in behavior) or an object `{"builder":25,"qa":15,"reviewer":40,"merge":15}`, where an absent stage key falls back to that stage's shipped default, so `{"reviewer": 90}` is a one-stage override rather than a new table. `resolveWatchdogMinutes` is the single reader, called at the moment the state machine judges ONE lane, so the two shapes can never leave half the loop reading a number the other half resolved differently. The defaults are derived, not chosen, from a new measurement over the same corpus #209 used: for every orchestrator-spawned agent plus its transitive descendants, the MERGED record timeline -- exactly the series `subtreeActivityMs` reports the newest of, since a lane is silent only when nobody in its subtree has appended -- and the largest gap in it. 1,143 real stage subtrees (builder 259, qa 293, reviewer 497, merge 94): builder max 608.0s, qa max 174.8s, reviewer max 1,161.1s, merge max 97.1s (`MEASURED_STAGE_SILENCE_MS`). Each default is 2x its family's own ceiling, floored at 2x the agent-level `MEASURED_MIDWORK_GAP_MS` and rounded up to the next 5 minutes: builder 25, qa 15 (the floor wins), reviewer 40, merge 15 (the floor wins). The floor is the load-bearing half -- a per-family sample is small, and shipping 2 x 174.8s = 6 minutes for QA because 293 QA subtrees happened to hold no long quiet stretch would kill any QA agent that sits on one slow build; the gate test pins every row against BOTH ceilings. Refusals tightened with the shape: an unknown stage key (`{"QA": 20}`) is a config error rather than a silently ignored line, because the per-key fallback would otherwise read as "I raised QA's budget" while QA quietly kept the default, and `0` stays refused in both shapes since "disable the watchdog" is the one reading this knob must never have. The CLI's `--watchdog-minutes` takes both shapes through the SAME validator config.json reads through -- no second, looser path into the state file -- and z-loop/SKILL.md Step 0 now JSON-stringifies the value, without which an object printed as `[object Object]` and coerced to `NaN`, and `elapsed > NaN` is false, i.e. the watchdog silently OFF for the whole run. `/z-setup` writes the table (not a scalar) when given no `--watchdog-minutes`, so the derivation actually reaches new projects.
- `watchdogMinutes` defaults to **15**, up from 10 (#256). The number only became meaningful with the fix above: as a stage-age timer 10 minutes was a guess at how long a whole stage takes, and as a silence budget it is answerable from the same measured population `SUBTREE_QUIET_MS` comes from — the longest gap between a working agent's own transcript records, `MEASURED_MIDWORK_GAP_MS` = 423,110 ms over 9,589 mid-work samples across 1,388 sub-agent transcripts. A silence budget under that ceiling declares a healthy agent dead, and this pack clears it by 2x wherever it decides anything on silence: 2 x 423,110 = 846,220 ms, rounded up to 15 minutes, identical to `SUBTREE_QUIET_MS` because it is the same question asked of the same evidence. The old 10 cleared it by 1.42x — on the decision that discards a whole ticket, where `SUBTREE_QUIET_MS`'s 2x only risks leaving one scratch worktree behind. A gate test pins the ratio. Projects with an explicit `watchdogMinutes` in `~/.zstack/projects/<slug>/config.json` are unaffected; re-running `/z-setup` without `--watchdog-minutes` picks up the new default.

### Fixed

- Every stage transition writes the board, so a resumed ticket with no lane behind it is re-claimed at the stage that actually ran instead of being rebuilt (#205). `/z-loop`'s `advance N to S` row re-stamped the lane lock, applied, and spawned the next stage — but never moved the ticket. From the first transition onward the board sat a stage behind its lane for the rest of the run: `/z-status` reported Building for tickets in QA or Review, and the in-flight-write marker `applyAction` stamps (`lastWroteStatus`, #125) never cleared, because ingest clears it only on seeing that write land — so what the design treats as transient GitHub latency became permanent, and the #116/#125 resync guard stayed armed for the life of the lane. The expensive consequence is the re-claim: `state.json` is authoritative only for a lane the loop still holds, and a ticket on the board with no lane behind it is re-claimed at the stage its BOARD status names (`lib/lanes.ts` `claimStage`) — the mechanism that lets a stopped lane resume at `qa`/`reviewer` instead of being rebuilt. Frozen at Building, that re-claim spawned a *builder* into a ticket whose build had finished and pushed, silently paying for the stage twice (#164 burned $1.35 duplicating already-pushed commits). The row now issues `"$Z_BOARD" move <N> <status> --if-present --slug "$SLUG"` as step 3, mirroring the `claim` row's #133 deferred commit, with `<status>` = `STATUS_FOR_STAGE[S]` — `builder`→Building, `qa`→QA, `reviewer`→Review, and `merge`→Review too, named explicitly because merge owns no column (Done means the PR landed), so an advance into merge re-writes Review and is a no-op on the board. Remembering the move is not left to prose: the derivation lives in code as `boardWriteFor(action)`, the one place that maps an Action to the write its row owes, and `loop apply` prints it in the tick output (`board write for #N = QA — … "$Z_BOARD" move N QA --if-present --slug <slug>`, the slug read off the state path because `resolveSlug` throws on a multi-project machine, and matched against the slug charset so a path segment holding a space or a metacharacter can never ride into that command line), so a skipped move is visible on the spot rather than a stage later as a rebuild. The reducer still issues nothing itself — `lib/board.ts` remains the pack's sole `gh` caller and `lib/loop.ts` stays pure. The row applies BEFORE it moves, which is a choice with two consequences: `canTransition` validates the transition first, so an advance that would write an illegal status throws exactly as it does today and the board is never touched; and a crash in the gap leaves the board one hop BEHIND a lane that names the write it owes, which is precisely the lagged-write shape `isOneHopLag` + the origin marker resync at that lane's next STAGE BOUNDARY (the guard only judges a lane with a recorded outcome, so the board stays behind for the rest of the running stage), keeping the lane, its stage and its bounce counters. Moving first would invert that window to board-ahead-of-lane, which the guard does not model, so it would `stop-lane` and drop a pending bounce's counter and note. 12 gate tests in `tests/loop.test.ts` (the AC1 write + marker-clear, the AC2 crash-and-resume end to end against a simulated orchestrator board, the illegal-transition throw, both crash-window resyncs, an exhaustive `Record<Action["kind"], …>` invariant that a lane carries a marker iff `boardWriteFor` names that exact write, and four CLI-print cases) and 5 doc canaries in `tests/loop-skill-fixes.test.ts`; deleting `boardWriteFor`'s `advance` case turns 7 of them red, including the resume, and reverting the advance row's move string turns 2 of the canaries red. `docs/user-guide/z-loop.md` and `docs/user-guide/troubleshooting.md` document the contract and the repair. Two residual costs this does NOT remove, each pinned by its own test rather than left to be rediscovered: `merge` owns no column, so the advance into it writes `Review` and a lane that died at the merge stage is re-claimed as a *reviewer*, re-paying one review of an already approved diff; and #130's `skip-qa` walk is the one advance that is not a single hop (Building→Review, while `PRECEDING_BOARD_STATUS` maps a reviewer lane's lag to `QA` alone), so a missed write on THAT advance still stop-lanes and re-claims as a builder — the pre-#205 outcome for every skip-qa advance, now narrowed to the crash window. Closing it means widening `isOneHopLag`, which this ticket's Out of scope list holds back. Out of scope and untouched: the `claim` row (already correct), `STATUS_FOR_STAGE` and the nine statuses, and the #125 guard's logic — which is correct given a truthful marker.
- The watchdog measures worker SILENCE instead of stage age, so a healthy stage is no longer probed for taking a long time (#256). `LaneState.lastActivityMs` was documented as "last observed worker output" but nothing in the pack observed a worker: it was written only by stage EVENTS — the claim, an advance, a #209 re-spawn, a recorded outcome, an ALIVE probe — so `watchdogExpired` fired `watchdogMinutes` after the stage STARTED however hard the agent was working. A QA stage is ordered to run typecheck, the full suite, and the build before it touches its first acceptance criterion (121s idle, 234s under load on this repo), so every QA stage crossed the old 10-minute default while perfectly healthy, and the machine's only answers there are `check-worker` and, on a dead probe, the `skip` that discards the ticket. The signal was already on disk and already parsed: the harness writes every sub-agent's transcript append-only, and #190's parentage walk already resolves which of them belong to one stage spawn. `lib/transcripts.ts` gains `subtreeActivityMs(subagentsDir, tag)` — the newest record timestamp across the stage agent and every descendant, sharing #209's tail parse rather than adding a second reader, and taken from the record's OWN clock because collection copies transcripts and an mtime would make a copied one look freshly active. `bin/z-loop-tick` reads it once per live lane, after the ingest that settles the lane list and before the `next` that reads the baseline, and hands the number to a new pure reducer (`recordActivity`, CLI verb `loop heartbeat`) — the same split as `nowMs`, so no filesystem read enters the state machine. The move is monotonic: an observation older than the baseline changes nothing, and every fail-open answer (`undefined` for a missing session transcript, an unresolved spawn tag, a tag matching two roots, an unreadable subtree) is a no-op that leaves the lane on its stage-start floor, so an unobservable subtree degrades to exactly the old behavior and can never park a healthy lane. `watchdogExpired` keeps its signature, its injected clock, and its exactly-the-budget-is-still-alive boundary; only the meaning of the baseline changed.
- A lane whose ticket leaves the loop's reach mid-run is now stopped by an action instead of being filtered out of state (#273). Two positive observations take a ticket out of reach: it lands in a board status the loop does not drive (`partitionKnownStatus`, added by #226 for the columns a human adds), or a confirm-pass lookup proves it off the board (`confirmedGone`, #138). Both folded into `gone`, and `ingestBoardItems` then dropped their lanes with a bare filter and emitted no action at all — so nothing tore down the lane's background agent, nothing removed its `locks/ticket-<N>.json`, and nothing decided the worktree's fate. Three failures followed in order: the worker kept running unsupervised, still committing to `z/ticket-<N>-…`; `drainComplete` measures "still running" by `lanes.length`, so the drain went true underneath it and Step 7's first act is deleting merged `z/ticket-*` branches; and the surviving lock made the next run's `scanOrphans` report a crashed lane, so Step 0 refused without `--reconcile`, whose recovery then release-claims and parks a ticket back to Ready whose custom column a human chose on purpose. Removal is now an ACTION the orchestrator executes, not a filter the reducer applies behind its back: ingest **keeps** such a lane and marks it (`LaneState.goneReason`, the thirteenth lane field — `unsupported-status` carrying the observed string, or `confirmed-gone`) along with a minimal tombstone ticket, purely so the state machine can still name what it must stop; `nextAction` returns `stop-lane` for any lane carrying one, checked *before* the `!lane.outcome` skip that gates every other per-lane stop (the human-move stop can wait for a stage boundary because that ticket is still on the board and observable next tick — a gone one is not, so waiting is exactly the unsupervised-worker window this closes, and would wedge the drain forever if the worker never reported); and `applyAction`'s `stop-lane` drops the lane and the tombstone in the same write, which is the ordering the old code inverted and what stops tombstones accumulating across ticks. `drainComplete` needed no new clause — the retained lane keeps `lanes.length === 0` false, so Step 7 cannot fire while one is outstanding — and a gate test pins that the retention cannot be undone silently. The other `stop-lane` (a human's move to Blocked/Questions/Skipped/Done) is unchanged and still keeps its ticket, which is real and must stay terminal in state. A **laneless** ticket in an unknown status is byte-identical to before: nothing to tear down, so it is just removed with its one stderr note. The stop runs as its OWN pass (step 1a) ahead of every other per-lane transition, not inside the shared lane loop where a lower-indexed lane with a finished stage returned first and left the stray agent running for as many ticks as its neighbours had work. It carries two structural fields on the action, read off the JSON and never off the note (#209's rule): **`salvage`**, because this is the one `stop-lane` that fires MID-STAGE rather than at a stage boundary — the worker may be halfway through writing files it never committed, and releasing the lane lock makes the worktree an orphan the next reconcile force-removes — and **`dropTicket`**, which is what tells `applyAction` to remove the ticket. `dropTicket` is on the ACTION rather than read back off `lane.goneReason` because the SKILL hand-builds a stop-lane of this kind itself (the `--if-present` `moved:false` recovery) for a lane that never went through a marking ingest: keying off hidden lane state left that path's ticket in `state.json` at a workable status, so the very next `next` returned a `claim` and spawned a fresh **paid** agent into a ticket the board had just proved it does not have — a pre-existing defect this closes, with the SKILL row updated to emit the flag. `z-loop/SKILL.md`'s positive-evidence block no longer says a gone ticket's lane is "released" by the tick and now routes both arms to the `stop-lane` row that performs the teardown, and the confirm-pass note in `lib/loop.ts` lost the same false claim. `confirmTargets` skips a lane already carrying a mark, since a lookup can prove nothing new about a ticket a positive observation already resolved. 29 gate tests across `tests/loop.test.ts` (the ingest/stop/drain truth table, both arms, cross-lane stop priority, source precedence, the `(none)` status arm, an unrecognized future `kind` that stops the lane without fabricating either proof), `tests/safety.test.ts` (the lock is released exactly once, so the next run's scan is clean), `tests/loop-skill-fixes.test.ts` (the doc canaries, including that the hand-built recovery emits `dropTicket`) and `tests/z-loop-tick.test.ts` (one Action line, note on stderr, through the real wrapper); `docs/user-guide/z-loop.md` and `docs/user-guide/troubleshooting.md` document the lane teardown and the custom-column symptom. No eval: status-set membership and lane bookkeeping are both deterministic. Out of scope and unchanged: which statuses the loop drives, the stopped lane's worktree disposition, re-spawning the stopped worker (#245), and the ghost-lane mirror image (#202).
- The human-needed gate no longer trips at tick zero on a fresh state file (#203). `initialBatchTickets` — the set `humanNeededStatus` scopes its numerator to — is captured from `!prevByNumber.has(t.number) || (Ready && !claimedByOther)`, and with no prior `state.json` that first clause is true for **every** ticket on the board: measured on this repo's own 190-item board, 190 numbers captured against a real batch of 1, so 3 pre-existing parks (1 Blocked, 2 Skipped, all from earlier runs) read as 300% and the gate tripped before a single ticket was claimed. That contradicted the field's own documented contract, which says a park predating the batch "never inflates this batch's trip". The clause only ever meant "this batch just filed it" — a #133 Step-1 pre-commit park straight to Questions/Blocked/Skipped — and "absent from the prior state" can only carry that meaning when a prior state exists to be absent from; with `prev === null` it cannot tell "new because this batch created it" from "new because there is nothing to compare against". It is now gated on `prev` existing, which leaves the fresh capture as exactly the unclaimed Ready queue: the same filter `initialReadyCount` already used for the denominator, so numerator scope and denominator can no longer describe different sets. `humanNeededStatus` is untouched — the defect was the capture, not the arithmetic. The behavior when `prev` exists is byte-identical, which is what #150 and #138 depend on; the one-sided cost is that on a project's **first** run a Step-1 park is not counted, being indistinguishable from an older one, and every later run has a prev and counts it exactly as before. `batchTickets` (#131's allow-list) does **not** share the defect and was not changed: `selectBatch` never reads `prev`, it filters `isWorkableStatus && !claimedByOther`, so a fresh capture already excludes parked tickets — pinned now by its own test rather than left to inspection. Two existing cases modeled the #133 AC4 Step-1 park with `prev === null`, which is not the path Step 1 runs on (Step 3's ingest follows Step 1's board writes, so a real Step-1 park always has a prev); both moved onto the real path, keeping their assertions, and the two `z-loop-tick` end-to-end cases that fabricated a 300% trip out of pre-existing parks on a fresh state now seed a drained prior state so the trip they assert is a real one. 8 gate tests across `tests/loop.test.ts` and `tests/z-loop-tick.test.ts`, including the live repro through the real wrapper; `docs/user-guide/z-loop.md` now states that the numerator only ever counts tickets the batch itself parked, first run included. No eval: the trip is arithmetic over a snapshot.
- A stage that dies without an exit marker is no longer skipped when its worktree holds finished work (#209). The exit contract is parsed from the agent's final message, so a markerless one is CONFUSED — correct when the agent could not do the job, wrong when it simply never said it did. Run 11's #170 builder addressed both reviewer findings, backgrounded its own `bun test`, and ended its turn waiting on a run nobody could report back to; recording that outcome would have skipped a ticket whose fix (`lib/cost.ts` + `tests/cost.test.ts`) was sitting uncommitted in the worktree, discarding the $2.11 that spawn had already spent. Three gaps, one change. **Prompt** (`lib/stage-prompts.ts`): the builder, QA **and reviewer** prompts now state that verification runs to completion in the FOREGROUND and that ending a turn with a background job still pending is parsed as CONFUSED — the missing half of "run the gauntlet", since the loop sends a stage agent exactly one message by design and nothing can wake an agent waiting on a backgrounded gate. ### Fixed

A read that *fails* decides nothing — the flag and the last known login survive untouched — but it is still recorded as an attempt (`loop claim-confirm-failed`, the orchestrator's other row), because leaving the stamps alone would re-emit `confirm-claim` on every single tick: a `gh` call plus an agent turn per tick, strictly worse than the `wait` this replaced, and reachable for real (a deleted or transferred issue, an assignee set too large to page, any `gh` auth or rate-limit outage all throw out of `lookup()`). - The reviewer eval (`evals/reviewer/`) now measures **recall across many defects** instead of whether adversarial mode catches one planted needle single-pass approves (#183, following #108). The old contract could not be satisfied, and #108 spent four fixture redesigns and 16 real single-pass reads proving why: a planted defect must violate a stated acceptance criterion or the rubric cannot grade it, so the criteria list is a complete index into where the defect can be, and a reviewer with code execution audits each criterion against the code that implements it. Diff size was not the lever (433 lines in round 3, 529 in round 4, both caught), and the arithmetic agreed — single-pass and the skeptics are the same model on the same blinded inputs, so per-trial pass probability peaked near 47% even under generous independence assumptions. The eval now asks what the loop actually pays for: how much of what is wrong one review cycle surfaces. A new `fixtures/multi-defect` (735-line diff, a keyed rate limiter plus its HTTP middleware, 54 green tests) hides eight independent defects across five classes — ordering interaction, missing validation, absent reclamation, swallowed error path, unnormalized trust-boundary input, unit/spec violation, wrong metric event, and a test that passes without the change — each verified to reproduce and to be unexercised by the shipped suite. A trial passes when the adversarial run names strictly more planted defects than the single pass (a tie is not a pass), and the run passes at `ceil(0.8 × N)` wins, so the ≥4/5 bar is a ratio rather than a bare count that would make `run.sh 1` structurally unpassable. Two config knobs: `minReviewerConfidence` (default 70) and `reviewerBelowThresholdAction` (`block` | `retry` | `off`, default `block`). `REVIEW-APPROVE` now always carries a literal `confidence=<0-100>` token — self-assessed on a single pass, skeptic-aggregated on a super-truth pass — parsed deterministically (`parseReviewerConfidence`, `/\bconfidence=(\d{1,3})(?!\d)/i`, 0-100 else `null`). `resolveOutcome`'s new gate mirrors the existing `maxQaPasses` pattern: at/above the floor the approval falls through to the merge gate unchanged; below it (or with no parseable confidence — fail-closed) `block` parks Blocked with the exact note `truth-check failed (confidence X/100)` (or `... with no parseable confidence score` for a malformed approve), `retry` bounces to a fresh builder, and `off` disables the gate entirely. The reviewer's four-key input blindness (`REVIEWER_INPUT_KEYS`, `assertReviewerInput`) is untouched — confidence lives in the OUTPUT contract, never a smuggled input key.
- Discord notifications for the five loop events via `lib/notify.ts` (#60): `work-complete`, `human-pause`, `ticket-parked`, `safety-violation`, and `token-burn`. The orchestrator (`z-loop`/`z-plan` SKILL) posts exactly one event at each moment the state machine already surfaces (a park to Questions, a park to Blocked/Skipped, a wedged/dead worker, a quota abort, a deadlock break, the end-of-loop report); the pure decision code (`loop.ts`, `endloop.ts`) stays network-free. - Human-needed mid-run safety control (issue #63): a `humanNeededPercent` config knob (default 30, `0` disables) trips when `(Blocked + Skipped + Questions) / initialReadyCount * 100` exceeds it, where `initialReadyCount` is the batch's committed-to-Building size captured once at Step 3's ingest and carried across every re-ingest for that batch. The reset is two-part, not just "the prior batch fully drained": `ingestBoardItems` only recomputes when there is no prior state at all, OR the prior state was `drainComplete` **and** the incoming board snapshot shows new, unclaimed Building tickets (the batch-commit step moves a whole new batch to Building before its first ingest, so any unclaimed Building ticket in a post-drain snapshot IS that new batch; a lingering `claimedByOther` Building ticket belongs to another session's batch and does not count). A drained prior state whose incoming snapshot is still all-terminal — e.g. the confirmation tick right after the batch's own last ticket parks/completes, which leaves `drainComplete` true in that same write — is the SAME batch's final state, not a new one, so its counters (and the fire-once flag) are preserved; this is exactly the batch's highest-value crossing (the last ticket tips it over) and the case a naive "drainComplete alone resets" implementation silently swallowed. The pure predicate (`humanNeededTripped`) and a read-only snapshot (`humanNeededStatus`) live in `lib/loop.ts`, which stays network-free; `bin/z-loop-tick` polls the breakdown every drain tick (the same per-iteration cadence #57 already collapsed into one call) and fires exactly one `human-needed` Discord notification through #60's `lib/notify.ts` transport the instant the threshold first crosses, marking the fire-once flag (`loop.ts human-needed-ack`) only after the send actually reports `sent` — an unconfigured project or a down webhook never wedges the ack, and never blocks the drain. `human-needed` is a seventh first-class `notify.ts` event (following #68's `plan-complete`), independently toggle-able via `notifications.events` like the other six.
- `/z-update` (and `bin/z-update` beside `setup`) updates an installed zstack in place.
